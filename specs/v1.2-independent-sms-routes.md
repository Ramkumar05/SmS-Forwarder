# V1.2 draft: Independent SMS forwarding and web archive routes

Status: **DRAFT — discuss UI and approve before implementation.** This document proposes V1.2 behavior. Once approved, incorporate it into `requirements.md`, `design.md`, `tasks.md`, and `CLAUDE.md` before changing app code. V1 and V1.1 descriptions remain historical; where they conflict, this approved V1.2 specification will govern V1.2.

## Goal

For every newly received SMS, evaluate two independent routes: forwarding by SMS and sending the original SMS to the private Cloudflare API. Each route has its own enable switch, match mode, and comma-separated body keywords. Neither route depends on the other route's result.

## Confirmed decisions

- Each route offers **All SMS** or **Only matching keywords**.
- Keyword lists are separate for SMS forwarding and the web archive.
- Keywords come from a comma-separated field. Trim surrounding whitespace, ignore empty entries, and match any one keyword as a case-insensitive substring of the **SMS body only**. Never match the sender. A phrase such as `payment received` is one keyword. A literal comma cannot be part of a keyword.
- The web route uses the original incoming SMS body, sender, and receive time. It can run when SMS forwarding is disabled, skipped for a loop, delayed, or unsuccessful.
- The web route makes one best-effort API attempt. If the phone is offline or the API request fails, discard that web delivery. Do not hold it for a later retry or backfill.
- Switching the web route off removes any locally pending web deliveries. Switching either route on processes only messages received from then onward.
- When both routes are off, ignore newly received SMS messages without saving them.
- Keep the existing SMS forwarding delay, retry, loop prevention, and seven-day forwarding log behavior unless a V1.2 requirement explicitly changes it.

## Proposed UI for discussion

Keep the main screen focused on current state and the forwarding log. Show two compact status rows at the top: `SMS forwarding: On · Matching keywords` and `Web archive: On · All SMS` (or their off states), plus a **Settings** action. Rename the existing log heading to **Forwarding activity** so web-only messages are not mistaken for missing log entries. Put the complete configuration in Settings, in two clearly separated sections:

```text
Settings

SMS forwarding                              [On/Off]
  Send to              [+91 ...]
  Which messages?      (●) All SMS  ( ) Matching keywords
  Keywords             [bank, payment received, otp]
  Send delay           Instant / 15 seconds / 30 seconds

Web archive                                 [On/Off]
  Which messages?      ( ) All SMS  (●) Matching keywords
  Keywords             [bank, receipt]
  Archive write token  [••••••••••] [Show]
  Delivery note        One attempt; offline or failed requests are dropped.

                         [Save settings]
```

Show each route's keyword field only when **Matching keywords** is selected. The field should explain `Separate keywords with commas; any one match is enough.` Keep disabled routes' configured number, modes, keywords, and token so the user can turn them on again without retyping. A route can be enabled only when its required number/token is present and, in keyword mode, it has at least one nonempty keyword. Show validation next to the relevant field. The write token is masked by default and must never appear in logs or diagnostics. The Settings save operation applies the two route configurations together so there is no partially saved state.

### UI choice to approve

This draft proposes **status rows on the main screen and switches in Settings**. The existing main-screen forwarding switch would move to Settings. An alternative is to keep quick switches for both routes on the main screen as well. Choose one before the UI task starts.

Another behavior to confirm: when SMS forwarding is switched off, should previously scheduled delayed forwards and retries be canceled and their pending bodies deleted, or should they finish? This draft leaves that choice open; new messages are never queued while the switch is off.

## Routing decision table

| Forwarding route | Web route | Result for a newly received SMS |
|---|---|---|
| Off | Off | Ignore; save no message or log row. |
| Matches | Off | Forward and log under existing SMS rules. |
| Off | Matches | Attempt the API once; create no forwarding log row. |
| Matches | Matches | Schedule SMS forwarding and independently attempt the API. Neither waits for the other. |
| Does not match | Matches | Attempt the API only. |
| Matches | Does not match | Forward only. |

`Matches` means the route is on and either set to **All SMS**, or set to **Matching keywords** with at least one body keyword match. The SMS loop-prevention check applies to forwarding only. A message from the forwarding target can still reach the web archive if the web route matches it.

## Functional requirements and acceptance criteria

**R12. Separate configuration.** Persist each route's enabled state, match mode, and keyword list independently. Persist the forwarding target and delay, and the archive write token. On upgrade, preserve existing forwarding settings and token. Default the new web switch to **Off** until the user explicitly enables it. No messages received before enablement are sent later. A disabled route has no effect on the other route.

**R13. Keyword matching.** Parse comma-separated input consistently: trim entries, omit blanks, compare case-insensitively against body text, and match if any entry is contained in the body. Empty body does not match keyword mode. All SMS mode does not require keywords. Sender text must never cause a match. Test mixed case, phrases, extra commas/spaces, empty input, and non-Latin text.

**R14. Forwarding route.** A matching SMS follows the existing forwarding behavior, including target validation, delay, loop prevention, three-attempt send retry, deduplication, and log. A nonmatching SMS does not create a forwarding work item or forwarding log entry. Turning forwarding off prevents new forwarding work; it does not change already completed sends.

**R15. Web route.** A matching SMS is eligible for one POST to the existing private Cloudflare `POST /api/messages` API using the saved `WRITE_TOKEN`, original sender/body/receive time, and deterministic idempotency key. Attempt it independently of the SMS route. If connectivity is absent at receipt, skip the web delivery immediately. If connectivity is lost before the attempt, or the request fails by transport error or any non-success HTTP response, discard it without retry. Do not schedule network-constrained work that waits for connectivity. A successful or failed web attempt must not change SMS forwarding status.

**R16. Storage and disabling.** Do not persist new SMS data when both routes are off. Never put the full body in WorkManager input, Logcat, a notification, or the forwarding log. A matched web message may exist in app-private transient storage only until its single attempt completes. If the work has not begun within five minutes, discard it; clean up any orphaned transient row after interruption, without replaying it. When the web route is turned off, cancel its pending work and delete all transient web bodies. Already archived server messages remain on the server. Preserve the SMS route's pending body only as required for its existing send retries.

**R17. UI and upgrade.** Settings shows two clearly separated route sections and validates each enabled route. The main screen clearly reports both route states and labels its log as forwarding activity. Remove the V1.1 `Uploads waiting` display because V1.2 has no offline backlog. The V1.2 database migration preserves forwarding history and pending SMS sends while deleting V1.1 queued web uploads. Tests verify this migration and the transition from V1.1 settings.

## Incremental tasks — one at a time

**T12. Approve V1.2 specification and UI.** Review this draft, resolve the main-screen switch placement and any wording changes, then update the canonical project specs. Done when requirements, design, tasks, and hard rules agree on independent routing and no web retry queue. No app code changes.

**T13. Settings model and UI.** Add persisted route settings and the two Settings sections, with validation and UI tests. Do not change SMS reception behavior yet. Done when both configurations survive restart and invalid enabled routes cannot be saved.

**T14. Pure matching policy.** Implement one reusable body-keyword matching policy and route-decision tests. Done when the R13 cases and all combinations in the decision table pass without Android dependencies.

**T15. SMS forwarding route.** Apply the forwarding decision at receive time while preserving send, retry, dedupe, and log behavior. Done when matched messages forward as before and unmatched messages cause no forwarding work or log row.

**T16. Independent web route.** Decouple API delivery from forward completion; replace the V1.1 retry queue with one best-effort attempt and cleanup. Done when web-only messages can upload, forwarding failure does not block upload, offline/API failure is dropped, disabling removes pending web data, and no message is replayed at startup.

**T17. End-to-end verification and release.** Run unit and emulator tests, test all route combinations and the V1.1-to-V1.2 migration, build a signed APK using the existing release key, and document remaining real-phone checks. Do not deploy or push until the user has reviewed the result.

## Out of scope

- Sender-based filtering, regex rules, and matching all keywords.
- Reading old SMS or backfilling messages received while a route was off.
- Offline web delivery, web retries, or guaranteed arrival in Cloudflare.
- Deleting messages already stored in the Cloudflare database.
- Changes to the separate Cloudflare Worker API unless its existing contract prevents this design.
